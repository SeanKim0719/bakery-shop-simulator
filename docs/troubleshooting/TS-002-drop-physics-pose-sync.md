# TS-002. 박스를 내려놓으면 플레이어가 위로 솟는다: 물리 엔진이 아직 옛 자리를 보고 있던 문제

- 분류: 물리·충돌
- 발견 시점: M1 플레이 테스트 (2026-11)
- 결과: 발 앞에 내려놓으면 플레이어가 솟고 가끔 박스가 날아가던 문제가 사라짐. 첫 번째 가설이 틀렸음을 확인하고 두 번째 수정에서 해결
- 관련 이슈: [#3](https://github.com/SeanKim0719/bakery-shop-simulator/issues/3), 수정 [PR #49](https://github.com/SeanKim0719/bakery-shop-simulator/pull/49)

> 초안이다. 수정 전후 GIF와 재현 횟수(10번 중 몇 번)는 직접 확인한 값으로 채운다. "배운 점"은 면접에서 직접 말할 내용이므로 자기 말로 다시 쓴다.

## 현상

- 박스를 든 채 발 앞 바닥을 내려다보고 내려놓으면 플레이어가 위로 솟는다. 가끔은 박스가 멀리 날아간다.
- 바로 아래(발밑)에는 내려놓을 수 없고, 거기서 조금 앞을 보면 내려놓을 수 있는데 그때 일어난다.

## 첫 번째 가설과 수정: 틀렸다

**가설 1.** 내려놓을 공간을 검사하는 `Physics.CheckBox`가 CharacterController의 반지름(0.35m)만 보고 스킨 두께(0.08m)는 보지 않는다. 그래서 검사는 통과하지만 실제로는 몸 가장자리에 박스가 놓이고, CharacterController가 겹침을 풀면서 박스 위로 올라탄다.

그럴듯했다. 스킨은 실제로 쿼리에 잡히지 않고, "몸에 걸치게 놓았을 때" 생긴다는 현상과도 맞았다. 그래서 반지름 + 스킨 크기의 캡슐과 상자가 겹치는지 직접 계산하는 검사(`PlacementMath`)를 넣었다 (`ba0edc2`).

**결과.** 수정이 들어간 뒤에도 버그가 그대로였다. 바로 아래에는 놓을 수 없게 되었으니 검사는 동작했다. 그런데 검사를 통과한 자리에 놓아도 플레이어가 솟았다.

이 수정은 **직접 확인하지 않고 넣었다.** "아마 가설 1이 맞을 것"이라고만 하고 넘어간 것이 한 번의 헛수고가 되었다.

## 다시 따져 보기

캡슐 검사를 통과한 자리는 박스와 몸 사이가 8cm 이상 떨어져 있다. 박스가 정말로 그 자리에 놓였다면 플레이어가 밀려 올라갈 이유가 없다. 그렇다면 **충돌이 켜지는 순간 박스가 다른 곳에 있었다**고 봐야 한다.

내려놓는 코드는 이랬다.

```csharp
transform.SetPositionAndRotation(position, rotation);   // 1. 놓을 자리로 옮긴다
SetCollidersEnabled(true);                              // 2. 충돌을 켠다
_body.isKinematic = false;                              // 3. 물리를 켠다
```

**가설 3.** Unity는 `Physics.autoSyncTransforms`가 꺼져 있으면(기본값) Transform의 변경을 **다음 FixedUpdate 직전**에야 물리 엔진에 반영한다. 1번에서 Transform은 옮겨졌지만 물리 엔진은 박스가 아직 "들고 있던 자리"에 있다고 알고 있다. 그 상태에서 2번이 충돌을 켠다.

들고 있던 자리는 카메라 앞 0.9m, 아래 0.3m다. 정면을 볼 때는 몸 밖이지만, 아래를 내려다보면 이 점이 몸 쪽으로 돌아 들어온다. 60도 아래를 볼 때 박스 중심은 몸의 축에서 0.19m, 높이 0.67m에 있다. 플레이어 캡슐(반지름 0.35m)의 한가운데다. 들고 있는 동안에는 충돌이 꺼져 있어서 문제가 없었지만, 내려놓는 프레임에는 **몸 한가운데에 충돌체가 생긴다.** 같은 프레임에 플레이어가 움직이면서(`CharacterController.Move`) 이 겹침을 풀려고 밀려 올라간다.

현상과 맞는 점:

- 발 앞에 내려놓을 때만 눈에 띈다 → 발 앞을 보려면 깊이 내려다봐야 하고, 그때 박스가 몸 한가운데에 있다.
- 가설 1의 수정으로 고쳐지지 않는다 → 놓을 자리의 검사와는 상관이 없다.

## 검증

가설 3이 맞다면 **코드를 고치지 않고 설정 하나만 바꿔도** 버그가 사라져야 한다. Transform의 변경이 늦게 반영되는 것이 원인이라면, 항상 바로 반영되게 하면 되기 때문이다.

| 조건 | 코드 | Auto Sync Transforms | 결과 |
| --- | --- | --- | --- |
| A | 수정 전 (`f3eda85`) | 끔 (기본값) | 플레이어가 솟고 박스가 날아간다 (10번 중 번) |
| B | 수정 전 (`f3eda85`) | **켬** | **버그가 사라진다** |
| C | 수정 후 (PR #49) | 끔 (기본값) | 버그가 사라진다 (10번 중 번) |

A와 B는 코드가 같고 설정만 다르다. 그래서 원인은 "Transform의 변경이 물리 엔진에 반영되는 시점"으로 확정했다.

확인한 것과 확인하지 못한 것을 구분해 둔다. **확인한 것**: 동기화 시점이 원인이다 (A와 B의 차이). **추정인 것**: 플레이어를 밀어 올리는 주체가 CharacterController의 겹침 해소라는 부분. 물리 엔진 내부의 동작이라 직접 보지는 못했다.

## 해결

충돌을 켜기 **전에** 물리 엔진 쪽 자세를 직접 맞춘다 (`HoldableObject.OnDropped`).

```csharp
transform.SetPositionAndRotation(position, rotation);

_body.position = position;        // 물리 엔진 쪽 자세를 직접 맞추고
_body.rotation = rotation;
Physics.SyncTransforms();         // 바로 반영한 다음에

SetCollidersEnabled(true);        // 충돌을 켠다
_body.isKinematic = false;
_body.interpolation = RigidbodyInterpolation.Interpolate;   // 보간은 자세를 맞춘 뒤에
```

**검증에 쓴 설정(Auto Sync Transforms)을 켜 두는 것으로 끝내지 않은 이유.** 프로젝트 전체에 걸리는 설정이라, Transform이 바뀐 뒤의 모든 물리 쿼리가 동기화를 확인하게 된다. 손님 수십 명이 움직이는 영업 중에는 낭비다. 문제가 되는 곳은 "Rigidbody가 붙은 물건을 순간이동시키고 바로 충돌을 켜는" 한 곳이므로 그곳에서만 직접 동기화한다.

가설 1에서 넣은 캡슐 검사는 지우지 않았다. 원인은 아니었지만 몸과 겹치는 자리를 막는 안전장치로는 맞는 동작이다.

## 다시 생기지 않게

- [코드 작성 규칙](../CONVENTIONS.md#뷰-monobehaviour)에 추가: Rigidbody가 붙은 물건을 순간이동시킬 때는 충돌을 켜기 전에 `Rigidbody.position`을 맞추고 `Physics.SyncTransforms()`를 부른다.
- 같은 문제가 생길 자리를 구현 계획에 미리 적었다:
  - 배송 박스 여러 개를 한 프레임에 놓을 때 ([M3-02](../plan/M3-production-loop.md)): 방금 놓은 박스가 다음 박스의 빈자리 검사(`Physics.CheckBox`)에 보이지 않으면 같은 자리에 겹쳐 놓인다.
  - 세이브를 불러와 박스와 트레이를 되살릴 때 ([M6-02](../plan/M6-save-and-polish.md)).
- 이 버그는 물리 엔진의 실행 순서에 달려 있어서 EditMode 테스트로는 고정하지 못한다. PlayMode 테스트를 도입하면 "내려놓은 프레임에 플레이어의 높이가 변하지 않는다"로 고정할 수 있다.

## 배운 점

- **가설은 확인하고 나서 고친다.** 가설 1은 그럴듯했고 수정도 깔끔했지만 틀렸다. 수정 전에 Scene 뷰로 "박스가 정말 스킨 안쪽에 놓이는가"를 한 번만 봤어도 알 수 있었다.
- **수정이 듣지 않으면, 그 수정이 보장하는 것에서 다시 출발한다.** "검사를 통과한 자리는 몸에서 8cm 이상 떨어져 있다 → 그런데도 겹친다 → 박스가 그 자리에 있지 않았다"로 범위를 좁혔다.
- **코드를 고치지 않고 가설만 시험하는 방법을 먼저 찾는다.** 설정 하나를 켜서 원인을 확정한 뒤에 코드를 고쳤다. 그래서 "고쳤더니 우연히 사라졌다"가 아니라 "이것이 원인이었다"고 말할 수 있다.
- Unity에서 Transform과 물리 엔진은 같은 물건을 따로 기억하고 있고, 둘이 맞춰지는 시점은 정해져 있다. 그 사이에 충돌을 켜거나 물리 쿼리를 하면 옛 자리를 보게 된다.
