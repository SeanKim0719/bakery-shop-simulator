# 0009. 수치는 `content.json` 한 파일에 두고 ScriptableObject로 가져온다

- 상태: 확정
- 날짜: 2026-11-11

## 상황

레시피 10종, 재료 12종, 상품 10종, 확률표 2개, 손님 성향 3종, 해금 9종과 수십 개의 설정값이 있다. v1 설계는 이 수치를 ScriptableObject 인스펙터에 직접 입력하는 방식이었다. 한편 밸런스를 구현 전에 확인하려고 파이썬 시뮬레이터를 만들었는데, 시뮬레이터도 같은 수치가 필요하다.

## 선택지

1. **인스펙터에 직접 입력**: Unity의 기본 방식. 에셋 40여 개를 손으로 채워야 하고, 시뮬레이터용 수치를 따로 관리해야 해서 둘이 어긋난다. 수치 변경이 git diff에서 잘 보이지 않는다.
2. **런타임에 JSON을 직접 읽기**: ScriptableObject 없이 JSON만 쓴다. 아이콘·프리팹 같은 에셋 참조를 JSON에 적을 수 없어 별도의 연결 방법이 필요하다.
3. **JSON이 수치의 원본, 에디터 임포터가 ScriptableObject를 갱신**: 수치는 JSON에서 오고, 외형(아이콘·프리팹)은 인스펙터에서 연결한다.

## 결정

3번. `Assets/_Project/Data/content.json`이 모든 수치의 원본이다. 에디터 메뉴 **BakeryShop → 콘텐츠 가져오기**가 `Data/Generated/`의 ScriptableObject를 만들거나 갱신한다. 같은 ID의 에셋은 수치만 덮어쓰고 외형 참조는 보존한다. 게임은 런타임에 ScriptableObject만 쓴다.

함께 정한 것: 가격 민감도와 시간대 곡선은 `AnimationCurve` 대신 점 목록의 선형 보간(`PiecewiseCurve`)을 쓴다.

## 이유

- 시뮬레이터와 게임이 같은 파일을 읽으므로 수치가 어긋나지 않는다. 수치를 바꾸면 시뮬레이션을 다시 돌려 영향을 바로 본다.
- 수치 변경이 텍스트 한 파일의 diff로 남는다. "왜 이 값을 바꿨는지"가 커밋으로 추적된다.
- 에셋을 손으로 채우는 반복 작업과 입력 실수가 없어진다.
- 점 목록은 JSON에 그대로 적을 수 있고, 순수 C#으로 계산해서 테스트할 수 있으며, 시뮬레이터와 결과가 정확히 같다.

## 결과와 트레이드오프

- 임포터(에디터 코드 약 200줄)를 만들고 유지해야 한다. 필드를 추가하면 JSON, 임포터, ScriptableObject 세 곳을 고친다.
- 인스펙터에서 수치를 고쳐도 다음 가져오기 때 덮어써진다. 생성된 에셋의 수치 필드는 인스펙터에서 읽기 전용으로 표시해 실수를 막는다.
- `ContentDatabase` 검증 테스트가 JSON의 오타(없는 ID 참조 등)를 잡는다.
