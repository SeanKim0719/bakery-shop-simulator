# 0004. 순수 C# 모델과 MonoBehaviour 뷰 분리

- 상태: 확정
- 날짜: 2026-10-15

## 상황

선반의 재고, 오븐의 굽기 상태, 손님의 판단 같은 규칙 로직을 어디에 둘지 정해야 했다. 3D 1인칭이라 화면에 보이는 오브젝트가 많고, 세이브와 테스트도 고려해야 한다.

## 선택지

1. **MonoBehaviour에 모두 넣기**: 직관적이고 빠르다. 대신 규칙을 테스트하려면 씬과 플레이 모드가 필요하고, 세이브할 때 오브젝트 상태를 긁어모아야 한다.
2. **모델(순수 C#)과 뷰(MonoBehaviour) 분리**: 규칙은 모델이, 표시는 뷰가 맡는다. 엔진 기능이 필요한 곳은 인터페이스로 경계를 둔다.

## 결정

2번. 모델이 진실을 갖고, 뷰는 모델을 표시한다. 손님 이동처럼 엔진이 필요한 부분은 `ICustomerBody` 같은 인터페이스로 분리한다.

## 이유

- 재고, 가격 판단, 확률, 결제, 세이브처럼 버그가 나기 쉬운 규칙을 EditMode 테스트로 빠르게 검증할 수 있다.
- 세이브는 모델만 저장하면 된다. 뷰는 불러온 모델을 다시 그리기만 한다.
- 손님 FSM을 가짜 몸체로 돌려 "선반이 비었을 때", "줄이 길 때" 같은 시나리오를 재현할 수 있다. 트러블슈팅에서 문제를 재현하는 도구가 된다.

## 결과와 트레이드오프

- 클래스 수가 늘고, 모델 변경을 뷰에 알리는 연결(이벤트)이 필요하다.
- 모델과 뷰가 어긋나는 버그(예: 모델에서는 팔렸는데 화면에 빵이 남아 있음)가 새로 생길 수 있다. 뷰는 이벤트를 받으면 해당 칸을 모델 기준으로 통째로 다시 그리는 방식으로 어긋남을 줄인다.
